# 写作约定（提交信息 / 发行说明 / 文档）

三条硬规矩。它们对应的是真实的读者——

## 1. 提交信息：一行说清，细节放正文

GitHub 的**文件列表会把每个文件最新一次提交的标题印在文件名后面**，所以标题就是仓库门面。

- 标题**不超过 72 个字符**，格式 `<type>(<scope>): <一句话>`，例如
  `fix(home): 修复家目录权限被改坏导致无法新建文件夹`。
- **不要**把版本号、顿号罗列的多个修复、破折号解释塞进标题（`v0.2.9 —— 修 A + 修 B + 修 C` 是反面样本）。
- 想写的东西写进正文：症状、真因、验证方式。正文多长都可以，它不会出现在文件列表里。
- `tools/preflight.sh` 会检查 HEAD 的标题长度，超限直接 CI 失败。

## 2. 发行说明：写给用户，不是写给自己

发行说明的读者是**下载 APK 的人**。他们只关心三件事：

```markdown
# vX.Y.Z

## 修复 / 变更
- 用户能感知到的问题 → 现在是什么行为（必要时一句原因，但不要调试过程）

## 升级
- 覆盖安装还是需要卸载重装；安装后要不要再做一步（例如点一次「一键部署」）
```

**不要**写：本机/真机实测过程、我如何定位、内部脚本与补丁的名字、"我发现两个 bug" 之类的自述。
这些属于 `docs/`（例如 `docs/ANDROID-GATES.md`、`docs/TROUBLESHOOTING.md`）或 Mnemon 记录——
那才是它们该待的地方，发行说明里出现就等于把内部日志贴给用户看。

## 3. 文档分层：索引 + 细节，别开第五份

| 类型 | 放哪 |
|---|---|
| 关卡总表、防复发协议 | `docs/ANDROID-GATES.md`（索引，先读它） |
| 按症状检索的细节 | `docs/TROUBLESHOOTING.md` |
| 版本迁移步骤与回滚 | `docs/UPGRADE-0.1.5.md` |
| 面向用户的安装/使用 | `README.md`、`docs/INSTALL.md` |
| 历史现场记录 | Mnemon Documents（带 sourcePaths，不复制正文） |

新坑先补进关卡表（症状 / 真因 / 修法 / **机器检查**），再补细节文档。

## 提交前自检

```bash
bash tools/preflight.sh      # 语法、补丁目标、布局、版本一致性、payload、标题长度
```
